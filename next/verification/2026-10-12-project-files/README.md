# 0.2.0-alpha.6 本地工程验证

本轮增加本地工程打开、保存、可携带副本、定位和最近记录。运行结果入口为 [verification.json](verification.json)，未完成验收仅维护在 [统一交接文档](../../../docs/待验证项目交接.md) 的 `V2-Project-01/02`。

45 项功能检查通过：前端保存顺序与错误边界 32 项、工程复制 7 项、背景 4 项、最近记录 2 项。桌面类型检查及所改 Rust crate 检查通过；绑定由已有的 Rust 导出测试生成，保留仓库配置对生成文件的格式检查豁免。Markdown 人工复核。没有启动额外开发服务器。

`portable-copy-check.py` 从仓库内既有六秒合成工程复制测试源，在仓库外生成背景 PNG、贴图 PNG 和纯合成音频 WAV，再分别用 alpha.5 和 alpha.6 打包内导出器导出。新 CLI 与桌面菜单调用相同复制核心。复制改为内部相对引用，原工程文件哈希保持；已有目标再次保存被拒绝且副本哈希保持。随后将副本移动，并删除仅由脚本创建的测试源和外部测试素材，副本仍通过资源检查和完整导出。三份输出均为 1280×800、60 fps、360 帧；RGBA 与时间戳逐帧一致，解码后音频 SHA256 相同。最后又用最终签名包验证相对目标路径复制及导出，360 帧继续一致。

脚本的 `prepare` 和 `verify` 两个阶段依次接收对应打包导出器的完整路径；默认试用目录必须是新的。脚本拒绝覆盖已经存在的测试目录。输出视频、工程和素材位于 `~/Movies/Jianku Screen Next/试用 0.2.0-alpha.6/`，不提交用户画面或个人背景。移动后的工程在 `移动后/可携带工程.cap`，另有相对目标路径测试副本。JSON、解码日志和帧摘要留在此目录供复核；大视频不进入 Git。

两次完整构建均编译/打包成功，但包装器在开发签名环节失败；相应原始日志保留。解锁既有开发钥匙串后，对同一个最终编译包补签并严格验证，通过后复制到独立试用目录再验证。没有输出凭证、修改钥匙串安全策略或关闭旧版/Cap。开发签名不是正式公证。

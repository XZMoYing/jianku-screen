# alpha.31：工程打开与暂停重播

日期：2026-10-25。承接 alpha.30 的两项待办；不连接 Android、iPad、副屏或会议软件，素材均为独立合成工程。

## 修复

- 首次命令行启动现在解析工程参数并接入原有 macOS 启动队列。绝对路径、以发送方工作目录为基准的相对路径、本地文件 URL、中文与空格路径、多选和重复请求统一处理；兼容 .cap。启动时已经指定工程就直接打开对应编辑器，初始界面准备完成也能正确结束启动状态。无工程参数仍进入首页。旧 Qt 格式及网络 URL 不在本入口中解析。
- 运行中单实例请求使用发送方目录，能接收多个工程。macOS 单实例插件 2.3.4 在 Tokio 任务中执行阻塞的监听循环，直接在回调里生成异步打开任务可能将任务留在被阻塞线程的本地队列。实际测试第一次启动请求 32 秒没有显示编辑器，随后发出相同请求才显示。现将 macOS 回调派发到界面线程，再按现有流程生成编辑任务；Linux 维持原有界面线程派发，Windows 不新增适配工作。
- 打开元数据失败时恢复首页并提供中英文提示，避免启动参数被识别后只剩后台进程；原始文件不改写。
- 播放进度和停止事件现在在持有状态锁之后核对播放任务代次。暂停移除任务后，它的迟到进度不再改回播放位置；新任务开始后旧停止事件也不能使新播放误报空闲。准备阶段音频释放也处于相同的身份检查内。保持已有解码、画质、光标、缩放、阴影、3D 与动态模糊路径。
- 开始播放接口不再将已有的同步启动错误吞掉并返回成功。它不代表所有后续异步解码错误均能通过这个返回值上报。播放按钮补充真实的切换状态和无障碍名称。
- 安装脚本原来只匹配不带参数的主程序命令行，会漏掉通过工程参数启动的进程。现在同时匹配命令行结尾和工程参数前的空格，避免应用尚在运行时更换包。用实际带参进程对照确认旧检查漏认、新检查识别；没有在这次保护检查中执行安装。3 项现有安装脚本测试及该文件 Biome 检查通过，见 [安装保护](install-guard.json)。

## 验证

`cap-editor` 与 `cap-desktop` 编译检查通过；3 项原生播放事件测试及 12 项工程打开/启动队列测试通过。播放测试持有状态锁，让旧事件排队，再执行暂停回退或替换播放任务，验证迟到事件不会覆盖位置、释放新任务的音频或错误更改活动状态。桌面 TypeScript、Rust 格式及改动的 Biome 检查通过。

35 项相关前端测试（播放意图路由、准备播放交接、准备帧传输）通过。检查概要见 [checks.json](checks.json)。

打包 debug 的 8 类打开检查通过，原始页面事件见 [startup.json](startup.json)：绝对路径、中文空格相对路径、本地文件 URL、多工程及去重、无参数首页、运行中首个正常相对路径请求、系统文件事件、无效元数据恢复首页。冷启动使用实际进程退出和新进程身份确认，不能仅以不含参数的进程匹配表达式判断。系统文件事件可能同时创建首页与编辑器，这与直接参数启动的页面顺序不同。

彩色四段、含变速与自动缩放的合成工程进行了两轮各 12 次实际控件操作：播放、暂停完成、回退到起点、重新播放。每轮包含 9 次时间尺操作与 3 次回到开头按钮，回退后等待 40 或 150 毫秒。两轮均从第 0 帧重新开始，并继续显示到至少第 45 帧。第一轮见 [playback-first.json](playback-first.json)，最终界面线程派发修订后的第二轮见 [playback-final.json](playback-final.json)；操作脚本为 [playback-review.js](playback-review.js)。脚本记录传输元数据和画布实际绘制的帧号，没有绕过播放按钮或降低画质；这些结果检查状态与进度，不是稳定帧率基准。

优化版也通过了首次工程参数启动和运行中第一次相对路径截图工程打开，沿用原进程，不依赖额外通知或本地 `open_editor` 动作。后者见 [优化版运行中打开](release-activation.json)。优化版没有编译调试脚本入口；24 次控件重播记录来自打包 debug，优化版检查实际窗口、版本、签名与导出，不混淆两者的验证范围。

## 测试过程中发现的边界

第一次混合打开测试使用了上一阶段直接进入截图编辑器的自制 PNG 工程，其元数据 fps 为 30，通用打开因此按视频路由并报错。将这份测试工程改成原生截图的 fps 0 后，截图分流已通过；没有为配合测试修改产品的识别规则。该错误工程还暴露了原有异常编辑器的退出问题：没有标题保存器时，退出会等待确认超时。通过现有调试入口调用该错误窗口的 `close()` 后可正常退出；本轮没有把它当成普通窗口按钮的验收。后续继续修复异常/缺失素材工程的完整恢复与退出，不将本次正常工程测试当成它已解决。见 [测试数据边界](invalid-fixture.json)。

首轮运行中相对路径打开超时后，使用相同本地参数再通知一次，编辑器立刻出现；记录见 [warm-before.json](warm-before.json)。修复后已使用正常第二进程发送的首个通知复测通过，记录为 `warm-relative`，不把额外通知当作功能成功。

系统文件事件的调试测试最初未出现窗口。采样显示两个任务停在 `ui_review_script → std::fs::read_to_string → open`，读取的是文稿目录中的外部测试脚本。把同一脚本复制到 `/private/tmp` 后，系统文件事件通过，产品源码未再改变。文件访问限制是此调试阻塞的推断，不把它列为产品工程打开修复或忽略一次未通过的结果。正式优化包不编译此 debug 脚本入口。

短合成工程回放通过不关闭长 GOP 动态壁纸、音频/摄像头、长工程/复杂多轨及快速交叠命令的全部验收项；实际输出和正式版持续帧率仍需分开测量。Windows、正式签名及物理设备验收保持后置。

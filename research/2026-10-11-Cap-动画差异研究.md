# Cap 与 Screen Studio 的动画差异研究

2026-10-11｜内部技术对照。此次只研究与保存证据，没有更改产品实现或设置。

范围：默认二维运镜、光标移动/姿态/点击、对应运动模糊及画布搭配；新增 3D 运镜、文字和场景转场不属于本轮曲线对照。

**硬性要求：各种动画继续以百分之百复现已锁定参考版本为内部目标；产品文档和功能简介不得用竞品名称加“同款”等字样宣传。静态实现接近不能视为逐帧验收通过。**

## 结论与证据范围

Cap 的主要默认弹簧、点击前瞻、自动缩放区间和焦点分组，与本项目已定位的 Screen Studio 基线非常接近。当前最值得核对的分歧是光标时间补偿、旋转的处理顺序、点击形变，以及缩小时的模糊中心。默认画布搭配则属于另一组选择，可以与运动链分别评估。

这足以解释“主要曲线看起来接近，整体手感仍有差异”的可能来源，**尚不能确定哪一项导致用户的实际感受**。本轮没有在两款应用里导出同一组受控操作，也没有测量用户工程的生效配置。

用户补充：编辑器播放与导出视频都能感到异常，但尚不能描述具体原因。只读检查 `/Applications/Cap.app/Contents/Info.plist` 确认本机版本/构建号均为 **0.6.0**，与本轮源码基线版本一致；见[本机版本记录](evidence/2026-10-11-cap/installed-cap.json)。版本号核对不等于安装二进制与源码提交的构建溯源核对。该观感来自用户报告，不是本轮逐帧测量。后续优先核对输出轨迹、形变、模糊及原始素材时序；仅优化编辑器播放不足以解释导出中的相同感受。

## 1. 主要模型和数值相同的部分

数值均按刚度 / 阻尼 / 质量排列。Cap 的 `tension / friction / mass` 对应这一顺序，不能按源码字段排列直接抄表。

| --- | --- | --- |
| 默认普通光标移动 | Mellow：470 / 70 / 3 | 光标 Smooth 与基础对象：470 / 70 / 3 |
| 默认画面运动 | 200 / 40 / 2.25 | 画面 Focused 与基础对象：200 / 40 / 2.25 |
| 临近点击的光标移动 | 530 / 40 / 1 | 530 / 40 / 1 |
| 拖拽光标移动 | 1000 / 40 / 1 | 1000 / 40 / 1；触发条件细节不同 |
| 点击目标提前选取 / 加速窗口 | 500 ms / 175 ms | 500 ms / 175 ms |
| 自动缩放区间候选 | 点击前 300 ms，后 2500 ms；合并间隔 2500 ms；尾部 1000/800 ms 排除/限制 | 同组常量；边界取整与事件定义仍需核对 |
| 默认自动缩放倍率 / 边缘吸附 | 2× / 0.25 | 基础/回退值 2× / 0.25 |

Cap 的配置依据：[项目配置源码](https://github.com/CapSoftware/Cap/blob/6cfdd172cd53b1d6861852288c2192a8ab743687/crates/project/src/configuration.rs)、[轨迹处理](https://github.com/CapSoftware/Cap/blob/6cfdd172cd53b1d6861852288c2192a8ab743687/crates/rendering/src/cursor_interpolation.rs)、[区间生成](https://github.com/CapSoftware/Cap/blob/6cfdd172cd53b1d6861852288c2192a8ab743687/apps/desktop/src-tauri/src/recording.rs)、[镜头时间线](https://github.com/CapSoftware/Cap/blob/6cfdd172cd53b1d6861852288c2192a8ab743687/crates/rendering/src/zoom_spring.rs)。Screen Studio 依据见[结构化静态参数](parameters/桌面参数-官方3.7.5静态.json)。

**预设名称不能横向等同。** Cap 默认是 Mellow；它的另一个 Smooth 预设为 80 / 28 / 2.5，比 Mellow 慢很多。Screen Studio 的光标 Smooth 则是 470 / 70 / 3。比较时应记录生效数值，不能只把两边都选成 Smooth。

Cap 的 `ClickSpringConfig` 控制临近点击时的位置跟随，不是点击缩小的形变弹簧。Screen Studio 基础对象里的 `mouseClickSpring=700/30/1` 也不是已定位的点击缩小节点实际使用值。

## 2. 光标差异：目标时间、倾斜与点击形变

### 普通移动多了一次时间补偿

Cap 在没有临近点击覆盖目标时，读取 `当前时间 + friction/tension × 1000` 的原始轨迹目标。Mellow 参数对应 **148.94 ms**。切换临近点击或拖拽参数时，用系数 0.12 平滑改变这个补偿量。光标形状 ID 仍读取当前时刻，位置目标与形状采样时间分开。

Screen Studio 已定位的普通移动路径读取当前/之前事件；点击在 500 ms 内时转向点击坐标，尚未在这条路径定位到对应的通用 `damping/stiffness` 时间补偿。两边都具有点击前瞻，差异主要在普通移动阶段。

**感受推论：** 补偿能减少光标落后于素材的感觉，也可能使急转和停止附近的轨迹更早改变。匀速运动的滞后模型不能完全描述急停、急转；是否过早以及幅度多少，必须用真实事件和画面时间一起测量。149 ms 是目标采样偏移，不是所有场景里最终光标提前 149 ms。

源码定位：`cursor_interpolation.rs` 的 `spring_lag_ms`、`LEAD_SMOOTHING`、`build_smoothed_timeline`。

### 倾斜的计算顺序不同

Cap：已平滑光标位置 → 与 400 ms 前已平滑位置作水平差 → 乘系数并限制 ±20° → 直接交给光标 shader。

Screen Studio：规划后的光标目标 → 与 400 ms 前规划目标作水平差 → 乘系数并限制 ±20° → 将位置与 `rotateZ` 一起送入条件弹簧。

Cap 基础旋转系数为 0.15，参考基础对象为 0.5。Cap 把归一化坐标乘来源尺寸；参考捕获坐标的逻辑点/像素单位仍待完整核对，**不能用这两个裸系数直接宣布最终倾斜角相差几倍**。

**感受推论：** 将限幅放在弹簧之前或之后，会在高速移动触及限幅时产生不同姿态；回正也会受不同的目标时间影响。参考的旋转还有单独的弹簧状态，Cap 这一角度路径没有第二次角度弹簧。Cap 位置本身已经平滑，不能据此认定它必然突然回正。

Cap 定位：`lib.rs` 的 `cursor_x_axis_tilt_radians` 与 `cursor.wgsl`。参考 `OA → ok → Nt → C2/Cfe` 的层级已在[10 月 10 日复核](2026-10-10-编辑器与录制链路复核.md)确认，本轮再次读取分析副本。

### 点击形变是一种明确不同的曲线

Cap 用 `smoothstep(u)=u²(3−2u)`：在点击前 130 ms 逐渐缩至 0.8，按住时保持，松开后 130 ms 回到 1。它是规定时长的曲线。

参考在点击前 130 ms 改变缩放目标，外层点击/隐藏节点由 **300 / 30 / 0.3** 弹簧推进，并保留原有速度。它是改变目标后继续运动的状态系统，130 ms 是前瞻条件，不能当成形变完成时间。

在“已完全按住、零初速度、松开后恢复”的隔离公式示例中，130 ms 后 Cap 为 100% 大小，参考弹簧的连续公式约为 94.71%。**这个数值是说明曲线差异的数学例子，不是参考应用某帧的实测结果**；完整帧更新顺序、离散求解、连续点击和隐藏分支均未包括。

**感受推论：** Cap 点击反馈可能显得更短、更规整；参考点击具有不同的收尾时间与连续点击响应。偏好需要同样的单击/连击素材比较。

源码：[Cap 点击形变](https://github.com/CapSoftware/Cap/blob/6cfdd172cd53b1d6861852288c2192a8ab743687/crates/rendering/src/layers/cursor.rs)。

### 输入过滤也不同

Cap 删除 100 ms 窗口内、相邻段都小于 0.015 UV 的小幅反向点，并稀疏化高频或很小的移动事件。参考已定位的是查看后一个/后两个事件的曼哈顿距离过滤，基础阈值 500，不是 500 ms 的低通滤波。两者会保留不同的微小动作和折返点。

Cap 按主键按住状态启用拖拽参数；参考已定位路径按前一个移动事件是否为 `mouseDragged` 判断。按住尚未开始拖动、其他鼠标键和同时间事件都是边界差异，不能只凭拖拽弹簧相同认定一致。

## 3. 镜头与求解器：相同参数仍会产生不同路径

Cap 的[求解器](https://github.com/CapSoftware/Cap/blob/6cfdd172cd53b1d6861852288c2192a8ab743687/crates/rendering/src/spring_mass_damper.rs)使用解析弹簧解，保留速度。镜头每 8 ms 更新并缓存，分别对倍率、构图中心、活动强度运行弹簧，再将倍率和中心转换成边界；光标则按 60 Hz 预计算。相邻样本之间插值，不能把缓存频率直接当成最终视频帧率。

参考使用毫秒子步的半隐式 Euler，带相对精度、收敛估算与吸附条件；每帧先推进旧目标，再设置新目标和参数。参考镜头路径先求最终 `scale/position` 样式，再对数值字段进行弹簧处理。Cap 则先设置当前步目标再推进，两者时间更新顺序不同。

倍率和构图中心相乘得到位置的过程，与直接对最终位置运行弹簧并不总等价。焦点不变的单次缩放可以很接近；缩放同时换焦点、画面接近边缘、缩回后马上再次放大，需要专门对照。

隔离“固定目标、相同初始状态、60 Hz、1 秒”公式实验中，解析解与参考所记录子步规则的最大归一化位置差约为光标 0.88%、镜头 0.93%。实验忽略吸附、目标变化和浮点精度，**仅说明求解器数值差异存在，不构成用户观感原因的证明**。本轮优先级更高的是目标规划和各通道组合。

Cap 保留了缩回时最后一个构图中心，并在接近 1× 时预先对齐中心。这些做法也在帮助稳定镜头，不能把 Cap 描述为简单地让视口追着每个光标点移动。

## 4. 动态模糊：结构接近，细节仍不同

### 缩小时的模糊中心有明确分歧

Cap 的 `analyze_motion` 在“上一帧边界完全包含当前边界”时直接选上一帧矩形中心；其他情况求角点运动线交点，失败后回退中心，并把 UV 中心限制在画面内。

参考 `O2 → sG` 在边界不相同时寻找对应角点运动线交点，找不到时不加这条缩放滤镜。**已定位路径没有 Cap 的包含关系中心替代分支。**

一个可复查的几何例子：焦点保持在横向 80%，倍率 2× 缩到 1.9×。横向边界从 `[-0.8, 1.2]` 变为 `[-0.72, 1.18]`。当前被上一帧包含，Cap 算出的模糊中心在当前内容 UV 的 **48.42%**；角点运动线交点换算后仍为 **80%**。纵向可保持居中，使这一例子属于尺寸变化占优的缩放模糊。

**感受推论：** 非中心焦点缩回时，运动围绕一个位置发生，模糊却可能向另一个位置收拢，拖影与运镜方向产生微妙不一致。这是本轮值得优先做导出对照的一项。上述例子验证的是函数公式，不代表每次缩回都发生这种分歧。

### 同为 21 次平移取样，分布也不完全一样

Cap 光标和画面使用 `0, 1/20, …, 20/20` 共 21 个等权样本。参考所查 shader 是一个中心样本，再追加 `0/20, …, 19/20`，中心重复一次。归一化采样重心分别为运动向量的 0.5 和 0.45238，参考最大附加偏移为 0.95 倍，Cap 为 1 倍。

例如同为 50 像素向量，采样重心相差约 2.38 像素。形状、透明边缘、滤镜区域会进一步影响可见结果，不能把这个计算直接等同于肉眼拖影长度差。

### 父子运动与透明度路径不同

Cap 在当前画面变换下计算前后光标位置差，得到光标自身运动；参考按带模糊的父层递归扣除位移，并处理逐轴符号。移动和缩放混合时，父子层贡献需要共同测量。

两边的缩放样本都有 13 个上限和 `4p(1−p)` 权重；Cap 有明确的射线长度上限、画面中心限幅、固定噪声函数及 alpha 加权。参考的纹理 alpha、区域与伪随机输出仍未完整验证。源码注释里的“matches reference”是作者描述，不能代替像素对照。

Cap 定位：[运动分析](https://github.com/CapSoftware/Cap/blob/6cfdd172cd53b1d6861852288c2192a8ab743687/crates/rendering/src/lib.rs)、[画面 shader](https://github.com/CapSoftware/Cap/blob/6cfdd172cd53b1d6861852288c2192a8ab743687/crates/rendering/src/shaders/composite-video-frame.wgsl)、[光标 shader](https://github.com/CapSoftware/Cap/blob/6cfdd172cd53b1d6861852288c2192a8ab743687/crates/rendering/src/shaders/cursor.wgsl)。

## 5. 默认搭配为什么可能更合用户偏好

Cap 的 Rust 基础结构初始值是白色背景、留白/圆角为 0。新建屏幕工程还会执行 `apply_recording_presentation_defaults`，因此只读 `Default` 结构会误判实际画面：

- 默认工程优先使用录制时保存的桌面背景；取不到时尝试内置 `cities/sf.jpg`。显式用户预设和记住的动态渐变还有独立条件。
- 留白在相应条件下设为 10；该字段经 `padding/100 × 0.4` 换算，不能直接称为输出边距 10%。
- 显示器/窗口录制的圆角在相应条件下设为 7.5，默认形状为 Squircle；圆角半径按 `rounding/100 × 0.5 × 内容短边` 转换。
- 阴影基础强度 73.6，高级 size/opacity/blur 为 14.4/68.1/3.8。shader 将基础强度乘进每个分项；默认最大 alpha 乘子约 0.5012。尺寸和过渡宽度随内容短边变化。

Cap 阴影由圆角矩形距离场加 smoothstep 得到；参考已定位的阴影是黑色遮罩经多轮 Kawase 采样后乘强度，并有角度/距离偏移。**轮廓、衰减、空间范围和单位均不同**。不能把 Cap 的 blur=3.8 与参考的 blur=20 按大小判断软硬，也不能把两种阴影称为完全相同。

背景素材、留白、连续圆角和这类阴影的组合，可能比某个参考预设更合用户偏好。这个偏好与动态节奏可以同时成立。本项目可分别评估画布预设和运动链；本轮没有替换默认设置。

Cap 依据：[工程创建与默认覆盖](https://github.com/CapSoftware/Cap/blob/6cfdd172cd53b1d6861852288c2192a8ab743687/apps/desktop/src-tauri/src/recording.rs)、项目配置、画面 shader。参考默认的有效工程覆盖与圆角/留白单位仍有缺口，见[画布研究](画布与运动模糊.md)与[参考工程实测](参考工程实测值.md)。

## 6. WebUI 与动画质量的关系

0.6.0 使用 Tauri/Solid 界面，同时提供可选 GPUI 原生界面预览；主分支的界面分工已经变化。视频合成和本报告涉及的弹簧/轨迹逻辑位于 Rust，画面效果主要在 wgpu/WGSL 中完成。**界面使用网页技术不能单独解释这些动画差异。**

同样，编辑器播放时的帧间隔与导出视频的动画轨迹属于不同问题。用户已确认预览和导出都能感觉到异常，且本机版本为 0.6.0。后续以轨迹、形变、模糊、时间映射及原始素材时序为优先方向；不能由此排除捕获帧间隔或源素材自身的问题。

## 7. 下一步的判定方法

优先级与完成条件已经集中加入[待验证交接](../docs/待验证项目交接.md)，本报告不另建一份待办真源。

对照应固定来源、画布、帧率、倍率、裁切、光标大小和工程生效参数，分别做各自默认风格与统一风格两组。需要的动作包括无点击匀速/急停、反向、单击/连击、按住拖拽、非中心焦点缩回、缩放同时换焦点。先关闭模糊测位置/角度/尺度，再单独比较拖影，并比较预览与导出。原生事件坐标单位必须先统一。

本轮的数学示例可用 `python3 research/evidence/2026-10-11-cap/formula-check.py` 重算，结果在[formula-result.json](evidence/2026-10-11-cap/formula-result.json)。它们只验证公式示例，未执行 Cap 或 Screen Studio 的完整渲染链。上述观感推论在真实对照之前保持未验证。
